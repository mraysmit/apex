## Executive Summary

The APEX Visual Editor (Blockly-based) currently supports approximately **75 of ~155 APEX keywords** (~48% coverage). The editor covers core functionality for rule and enrichment authoring, and now includes:
- **Scenario configuration support** for workflow orchestration
- **Component references** for modular configuration management
- **Error recovery** for resilience and fault tolerance

Advanced features like rule chains and pipelines are not yet supported.

## Detailed Keyword-by-Keyword Implementation Plan

This section provides a comprehensive implementation plan for all APEX keywords, organized by priority and complexity. Each keyword is evaluated against the current implementation status in `apex_editor_main.html`.

### Visual Editor Design Philosophy

Before reviewing the implementation status, it's critical to understand the visual editor's design philosophy:

#### Implicit Type Derivation

The visual editor correctly implements the `type` keyword **implicitly through block selection**. This is the correct design pattern for a visual editor because:

1. **Reduces user error** - Users cannot accidentally set an invalid type
2. **Simplifies the UI** - No redundant dropdown that duplicates block selection
3. **Enforces consistency** - The block structure guarantees the correct type

| Block Selected | Generated `metadata.type` | Generator Location |
|----------------|---------------------------|-------------------|
| `apex_rule_config` | `"rule-config"` or `"transformation-config"` | Line 2802 - based on transformations presence |
| `apex_data_source_config` | `"data-source-config"` | Line 2879 |
| `apex_scenario_config` | `"scenario"` | Line 3403 |
| `apex_scenario_registry` | `"scenario-registry"` | Line 3519 |
| `apex_component_config` | `"component"` | Line 3588 |

Similarly, enrichment types are derived from block selection:
- `apex_enrichment_calculation` → `"calculation-enrichment"` (line 3139)
- `apex_enrichment_field` → `"field-enrichment"` (line 3162)
- `apex_enrichment_lookup` → `"lookup-enrichment"` (line 3193)

And data source types:
- `apex_data_source_database` → `"DATABASE"` (line 2920)
- `apex_data_source_rest` → `"REST_API"` (line 2951)
- `apex_data_source_file` → `"FILE_SYSTEM"` (line 2977)

And lookup dataset types:
- `apex_lookup_dataset_reference` → `"reference"` (line 3216)
- `apex_lookup_dataset_database` → `"database"` (line 3232)

#### Structural Generation

Many YAML keywords are generated automatically by the block structure, not as explicit fields:
- **Section keywords** (`rules`, `enrichments`, `transformations`, etc.) - Created by section blocks
- **Nested config keywords** (`connection-config`, `calculation-config`, `lookup-config`) - Generated by block generators
- **Array containers** (`rule-ids`, `enrichment-ids`, `field-mappings`) - Created via statement inputs

### Generator Updates Required

For each new field added to blocks, the corresponding generator function must be updated to include the new field in the YAML output. Example pattern:

```javascript
apexGenerator.forBlock['apex_rule_group'] = function (block, generator) {
    const id = block.getFieldValue('ID');
    const name = block.getFieldValue('NAME');
    const enabled = block.getFieldValue('ENABLED') === 'TRUE';
    const operator = block.getFieldValue('OPERATOR');
    const stopOnFirstFailure = block.getFieldValue('STOP_ON_FIRST_FAILURE') === 'TRUE';
    const parallelExecution = block.getFieldValue('PARALLEL_EXECUTION') === 'TRUE';
    const errorHandling = block.getFieldValue('ERROR_HANDLING');

    // ... rest of generator

    const groupObj = {
        id: id,
        name: name,
        enabled: enabled,
        operator: operator
    };

    // Conditionally add optional fields
    if (stopOnFirstFailure) groupObj['stop-on-first-failure'] = true;
    if (parallelExecution) groupObj['parallel-execution'] = true;
    if (errorHandling !== 'fail-fast') groupObj['error-handling'] = errorHandling;

    // ... rest of generator
};
```

### Design Principles for Future Implementation

When adding new keywords to the visual editor, follow these principles:

1. **Use implicit derivation for type keywords** - When a block represents a specific type, hardcode the type in the generator rather than adding a dropdown field.

2. **Use structural generation for wrapper objects** - Keywords like `connection-config`, `calculation-config`, `lookup-config` should be generated by the block structure, not exposed as fields.

3. **Only expose user-configurable values** - Fields should only be added for values that the user needs to explicitly set.

4. **Maintain consistency with existing patterns** - New blocks should follow the same patterns as existing blocks for similar functionality.
